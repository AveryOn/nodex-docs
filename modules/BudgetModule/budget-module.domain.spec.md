# BudgetModule Domain Specification

## 1. Overview

### Purpose

Решает задачу планирования расходов. Обеспечивает ведение бюджета в табличной форме с разделением записей по областям (scopes), тегам, блокам, статусам, датам и валютам.

Поддерживает суммирование записей независимо от валют с приведением к единой итоговой валюте для выбранного диапазона. Устраняет необходимость ручной конвертации и агрегирования.

Обеспечивает группировку записей по областям (scopes) для логически структурированного представления.

### Scope

В модуль входит:

- создание и управление записями Budget
- организация записей через BudgetBlock
- группировка записей по BudgetScope
- управление статусами записей через BudgetStatus
- задание порядка отображения через BudgetScopeOrder
- тегирование записей через Tag и BudgetTag
- работа с валютами через Currency (выбор, хранение, конвертация)
- суммирование записей с учетом мультивалютности

### Out of Scope

В модуль не входит:

- учет фактических транзакций (реальные списания из банков/кошельков)
- интеграции с банковскими API и платежными системами
- управление доходами (если не используется как отдельный сценарий)
- финансовая аналитика высокого уровня (прогнозы, отчеты, ML)
- управление пользователями и доступами
- хранение исторических курсов валют

### Module Responsibility

**BudgetModule** позволяет пользователю **фиксировать запланированные расходы** чтобы ничего не забыть и всегда видеть полную картину предстоящих трат

## 2. Ubiquitous Language

### Budget

Budget — доменная сущность, представляющая одну запись запланированного расхода с суммой, валютой, датой планирования, привязкой к BudgetBlock, BudgetScope, BudgetStatus и набором Tag; является атомарной единицей для агрегации и анализа

### BudgetBlock

BudgetBlock — доменная сущность более высокого уровня, предназначенная для логического и тематического объединения нескольких Budget записей. Используется как контейнер для структурирования бюджета, позволяя группировать связанные расходы в осмысленные категории (например: «Продукты», «Подписки», «Жильё»). Не содержит собственных сумм как источника истины, а агрегирует значения входящих Budget записей.

### BudgetScope

**BudgetScope** — именованная метка для группировки записей Budget внутри блока.

**Природа:** справочная сущность. Создаётся неявно через поле в форме Budget, без отдельного интерфейса управления.

**Поведение при создании:**

- пользователь вводит новое название -> создаётся запись в `budget_scope`, её id записывается в `budget.scope_id`
- пользователь выбирает существующий -> id существующей записи записывается в `budget.scope_id`
- пользователь ничего не указал -> используется системная запись с `name = main`

**Область видимости:** scope глобален в рамках одного пользователя (или группы пользователей) — один и тот же scope может использоваться в разных BudgetBlock.

**Чем scope не является:**

- не период (не содержит дат)
- не категория (не несёт семантики типа трат)
- не иерархия (нет вложенности)
- не обязательное поле ввода

### BudgetStatus

BudgetStatus — статус жизненного цикла записи Budget, определяющий её актуальность.

**Значения:**

- `active` — запись актуальна, `planned_at` в будущем или не задана
- `completed` — пользователь вручную отметил запись как выполненную
- `expired` — система автоматически присвоила статус когда `planned_at` стало меньше `now`

**Переходы:**

```
active -> completed   (пользователь вручную)
completed -> active   (пользователь, откат)
active -> expired     (система автоматически)
expired -> active     (пользователь, только если planned_at перенесена в будущее)
expired -> completed  (запрещено)
```



### BudgetScopeOrder

**BudgetScopeOrder** — сущность фиксирующая порядок отображения scope внутри конкретного BudgetBlock.

**Природа:** вспомогательная сущность. Не несёт бизнес-смысла сама по себе — существует исключительно для управления представлением.

**Область видимости:** локальна для блока. Порядок scope в Block A не влияет на Block B даже если scope одни и те же.

**Поведение:**

- пользователь вручную задаёт порядок scope внутри блока
- система сохраняет этот порядок в `budget_scope_order`
- при отображении Budget внутри блока scope сортируются согласно сохранённому порядку



### Tag

**Tag** — пользовательская метка для категоризации любых сущностей системы.

**Природа:** shared‑сущность. Существует независимо от любого модуля. Связь с конкретными сущностями реализуется через промежуточные таблицы вида `{entity}_tag`.

**Поля:**

- `name` — название тега
- `color` — цвет в HEX



**В контексте BudgetModule:** связь с Budget реализуется через `budget_tag` (many-to-many). Управление тегами частично доступно через форму Budget, в будущем — через другие модули системы.

### BudgetTag

**BudgetTag** — промежуточная таблица реализующая связь many-to-many между Budget и Tag.

**Поля:**

- `budget_id` — внешний ключ на Budget
- `tag_id` — внешний ключ на Tag

### Currency

**Currency** — системный справочник валют.

**Природа:** shared сущность. Управляется системой, не пользователем. Список пополняется через административный слой или код.

**Поля:**

- `id` — идентификатор
- `code` — код валюты (USD, GEL, EUR)
- `symbol` — символ валюты (\$, ₾, €)

**Связь с Budget:** один Budget имеет одну валюту через `currency_id`.

**Будущее расширение:** мультивалютное суммирование записей Budget с конвертацией через внешний API. Валюта итога выбирается пользователем.

## 3. Domain Model

### Main Entities

- `Budget`
- `BudgetBlock`
- `BudgetScope`
- `BudgetStatus`
- `BudgetScopeOrder`

### Supporting / Shared Entities

- `Tag`
- `BudgetTag`
- `Currency`

### Entity Roles

**Budget** — центральная сущность модуля. Представляет единицу запланированного расхода. Существует чтобы пользователь зафиксировал трату и не потерял её.



**BudgetBlock** — контейнер для группировки записей Budget по крупным темам. Существует чтобы пользователь не терялся когда записей становится много.



**BudgetScope** — метка для разделения записей внутри блока на логические группы. Существует чтобы пользователь мог структурировать записи внутри блока без создания новых блоков.



**BudgetStatus** — индикатор актуальности записи Budget. Существует чтобы пользователь понимал какие расходы ещё предстоят, какие выполнены, а какие просрочены.

####

**BudgetScopeOrder** — фиксатор порядка отображения scope внутри блока. Существует чтобы пользователь мог контролировать структуру списка и не получал хаотичный порядок областей



#### **Tag** — пользовательская метка для категоризации и поиска. Существует чтобы пользователь мог гибко группировать записи по смыслу независимо от блока и scope.

####

**BudgetTag** — связующая сущность между Budget и Tag. Существует только как техническая реализация связи many-to-many, собственной бизнес-роли не имеет.

####

**Currency** — справочник доступных валют. Существует чтобы система знала в какой валюте выражена каждая запись Budget и могла корректно отображать и суммировать суммы.



### Relationships Between Entities



**BudgetBlock -> Budget** Блок содержит записи. Без блока запись не существует. Один блок — много записей.

---

**Budget -> BudgetScope** Каждая запись принадлежит области. Если пользователь не указал область — запись попадает в `main`. Один scope — много записей.

---

**BudgetBlock -> BudgetScopeOrder** Каждый блок может иметь свой порядок областей. Порядок настраивается отдельно для каждого блока и не влияет на другие блоки.

---

**Budget -> BudgetStatus** Каждая запись всегда имеет статус. Статус отражает актуальность записи и меняется либо пользователем либо системой.

---

**Budget -> Currency** Каждая запись выражена в конкретной валюте. Валюта определяет как отображается сумма и как она участвует в суммировании.

---

**Budget -> Tag** Запись может иметь несколько тегов или не иметь ни одного. Теги помогают группировать и искать записи независимо от блока и области.

---

**Tag -> система** Тег существует независимо от любой записи. Один тег может быть привязан к записям в разных блоках и областях.

---

## 4. Invariants

### Global Invariants

- Budget всегда принадлежит одному BudgetBlock
- Budget всегда имеет статус — не может существовать без него
- тег существует независимо от любой записи Budget
- валюта записи определяется только из системного справочника — пользователь не может создать валюту

### Budget Invariants

- всегда принадлежит одному BudgetBlock
- всегда имеет статус — не может существовать без него
- всегда принадлежит одному BudgetScope — если не указан явно, используется `main`
- `expired` недостижим если `planned_at` не задан
- переход `expired -> completed` запрещён
- переход `expired -> active` возможен только если `planned_at` перенесена в будущее
- мягкое удаление — `deleted_at` фиксирует дату, запись не удаляется физически
- отображается только если `status = active` и `deleted_at IS NULL`

### BudgetBlock Invariants

- обязателен в системе, без него Budget не существует
- каждый BudgetBlock принадлежит одному владельцу
- название блока уникально в рамках владельца
- блок может существовать без записей Budget
- удаление блока запрещено, если в нём есть активные Budget (или требует переноса/архивации записей)
- блок может отображать сумму всех записей Budget 

  него в выбранной валюте либо в валюте по умолчанию \$ (USD)

### BudgetScope Invariants

- один и тот же scope доступен для отображения между блоками.
- **Жизненный цикл:**
  - scope не удаляется автоматически при удалении Budget если он с ним связан через scope\_id
  - удаление и редактирование scope — отдельный интерфейс управления (не реализован в MVP, планируется)

### Currency Invariants

- `code` уникален глобально
- `Currency` — системная shared-сущность и источник истины по валютам находится в БД
- справочник валют создаётся через seed и далее обновляется backend через API
- внешний API не является source of truth, он только поставляет данные для обновления
- `code` и `symbol` не подлежат обычному изменению
- валюта не может быть удалена, если существует в системе
- default currency жёстко зашита в системе
- курсы валют хранятся в БД и периодически обновляются
- при недоступности внешнего API используются последние сохранённые курсы из БД
- Budget не может существовать без `currency_id`
- пользователь не вводит валюту вручную, а выбирает только из системного справочника
- справочник валют глобален и не привязан к `org_id`
- система гарантирует возможность приведения любой поддерживаемой валюты к другой поддерживаемой валюте
- если конвертация не удалась, запрос завершается ошибкой
- используются только ISO-коды валют
- отображение валюты по умолчанию идёт через `symbol`, но формат отображения может настраиваться пользователем
- конвертация выполняется по курсу на момент запроса
- точность и правила округления — открытый вопрос

### Tagging Invariants

- Budget может существовать без тегов

- один Budget может иметь не более 5 тегов

- одна и та же связь `budget_id + tag_id` не может существовать дважды

- Tag глобален в рамках `org_id`

- имя тега уникально в рамках `org_id`

- имя тега нормализуется системой, регистр не сохраняет уникальность как отдельную семантику

- Tag можно удалить даже если он привязан к Budget

- при удалении Tag удаляются только связанные записи в `budget_tag`, Budget остаётся валидным

- редактирование Tag меняет его отображение во всех старых и новых связях

- Tag может быть создан из формы Budget

- создание Tag не является частью обязательной транзакции создания Budget

- при конкурентном создании одинакового Tag первый запрос успешен, второй получает конфликт (`409`)

- Tag может существовать без единой связи с сущностями системы

- не связанный ни с чем (orphan) Tag не удаляется автоматически

- `name` обязателен, ограничен 30 символами, пустое значение после trim запрещено, emoji в имени тега запрещены, спецсимволы в имени тега запрещены

- `color` необязателен

- если `color` не указан, система назначает его автоматически

- `color` допускается только в формате HEX. short HEX формат не допускается

- Tag является shared-сущностью и может использоваться для связи Budget с другими сущностями системы

- порядок тегов у Budget не имеет бизнес-смысла

- при soft delete Budget связи в `budget_tag` не удаляются

- при восстановлении Budget связи в `budget_tag` сохраняются и продолжают использоваться

## 5. Behaviors

### Budget Behaviors

- Создание Budget:

  - создаётся внутри выбранного BudgetBlock
  - обязательные поля: `title`, `amount`
  - `currency_id` по умолчанию = USD (или пользовательский default)
  - `scope_id` по умолчанию = `main`
  - `status` = `active`
  - `planned_at` опционален

- Переход статуса:

  - `active -> completed` выполняется пользователем вручную
  - запись исчезает из активного списка и доступна в истории

- Автоматический переход в `expired`:

  - выполняется системой (cron)
  - условие: `planned_at >= now`
  - не зависит от пользовательской активности

- Изменение данных:

  - `amount` может быть изменён пользователем
  - `currency_id` может быть изменён (значение `amount` не конвертируется)
  - `planned_at` может быть установлен или изменён

- Изменение scope:

  - пользователь может выбрать существующий scope или создать новый
  - при выборе нового scope создаётся запись в `budget_scope`
  - если scope отсутствует в блоке — создаётся запись в `budget_scope_order` с наименьшим приоритетом (в конце)

- Управление порядком (через scope):

  - порядок областей изменяется пользователем
  - изменения сохраняются в `budget_scope_order`

- Работа с тегами:

  - Budget может быть привязан к Tag (создание связи в `budget_tag`)
  - Tag может быть отвязан (удаление связи)

- Удаление:

  - soft delete: устанавливается `deleted_at`, запись скрывается
  - связи в `budget_tag` сохраняются
  - восстановление возвращает запись в исходное состояние
  - hard delete: физическое удаление записи и всех связей (по истечении срока или вручную)

- Агрегация:

  - участвуют только записи со статусом `active` и без `deleted_at`
  - поддерживаются виды:
    - по scope
    - по произвольному набору записей
    - единичная
    - полная по блоку
    - превью по блоку
    - по тегу
  - все операции мультивалютные
  - курсы берутся из БД

- Поведение по умолчанию:

  - если scope не задан — используется `main`

## 10. Open Questions

- Историчность scope для completed Budget. Если scope переименован, должны ли completed-записи показывать новое имя или историческое.

- Пользователь может перенести Budget в другой блок?

- Удаление scope с подтверждением. Нужно ли явное подтверждение, учитывая массовый перенос Budget в `main`.

- Scope без использования. Нужно ли предусматривать cleanup flow для неиспользуемых scope.

- Reserved names policy. Будут ли добавляться другие системные scope помимо `main`.

- Нормализация title. Требуется ли строгий whitelist спецсимволов и единая политика валидации.

- Конкурентное создание scope. Поведение при race-condition (200 / 409) должно быть явно зафиксировано.

- Создание BudgetScopeOrder для `main`. В какой момент гарантированно создаётся запись порядка для системного scope.

- Scope rename collision. Что делать при попытке переименовать scope в уже существующий title в рамках одного org\_id (ошибка или merge).

- Ограничения системного scope. `main` нельзя удалять, переименовывать или менять его системный статус — это нужно явно зафиксировать.

---

### Currency Open Questions

- Precision / rounding. Какой scale у сумм и курсов, и как именно выполняется округление.

- Time consistency курсов. Используется один курс на весь расчёт или курс на каждую операцию.

- Cache invalidation. Как определяется устаревание курса (TTL / timestamp / version).

- Частота обновления. Фиксированная (cron) или адаптивная.

- Частичный апдейт курсов. Что делать, если API вернул не все валюты.

- Atomicity обновления. Обновление курсов — атомарное или допускается частичное состояние.

- Fallback consistency. Курсы из БД — это единый снапшот или возможна рассинхронизация.

- Base currency. Есть ли базовая валюта, относительно которой считаются все курсы.

- Conversion path. Конвертация всегда через базовую валюту или возможны прямые пары.

- Drift при многократных конвертациях. Гарантируется ли обратимость A -> B -> A.

- Zero / invalid rate. Что делать при курсе = 0 или null.

- Currency activation. Есть ли флаг активности валют.

- Ограничение набора валют. Возможность ограничить список валют для пользователя в будущем.

- Версионирование курсов. Нужна ли история курсов или только последнее значение.

- Currency display fallback. Что показывать, если отсутствует symbol.

- API trust boundary. Кто валидирует данные от внешнего API.

- Sync race condition. Что происходит при параллельном обновлении курсов.

- Currency consistency invariant. Гарантируется ли наличие валидного курса для всех используемых валют.

- Error granularity. Падает ли весь расчёт при ошибке одной валюты (ожидаемо да, но нужно зафиксировать).

- Scaling. Выдержит ли модель при росте количества валют.
