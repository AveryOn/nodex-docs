# Nodex - полный собранный контекст

Проект нужен:

* для личного использования;
* как архитектурная практика;
* как потенциальный portfolio case;
* как система, которая помогает не забывать важные вещи;
* как единое место для задач, заметок, бюджета, напоминаний и личных записей.

Проект находится в ранней стадии. Формальной документации почти нет. `v1.0` только начал оформляться.

---

## 1. Главная проблема проекта

Зафиксированная проблема:

> без доменной фиксации можно неправильно определить сущности, связи, границы модулей и поведение системы.

Поэтому перед реализацией нужен промежуточный слой:

```txt
Domain Specification
```

То есть не сразу код, таблицы, DTO и API, а сначала:

* scope;
* словарь терминов;
* сущности;
* инварианты;
* поведение;
* use cases;
* decision rules;
* boundaries;
* open questions.

---

## 2. Правильный порядок работы

Ранее был зафиксирован такой порядок:

```txt
1. Зафиксировать сырые мысли
2. Превратить их в domain spec
3. Уточнить сущности
4. Уточнить инварианты
5. Уточнить сценарии
6. Только потом проектировать БД/API/сервисы
```

Смысл: сначала понять домен, потом писать архитектуру и код.

---

## 3. Сценарий 1 - быстрая фиксация важной информации

пользователь хочет иметь возможность быстро фиксировать информацию, когда:

* кто-то что-то говорит;
* пользователь чувствует, что это важно;
* есть риск, что пользователь это забудет.

Это может быть:

```txt
срочное
бессрочное
```

По сути это **быстрая заметка**.

Смысл:

```txt
важно -> быстро зафиксировать -> потом не потерять
```

Это не обязательно задача. Это может быть просто фрагмент информации.

---

## 4. Сценарий 2 - журнал операций / событий / бытовых действий

пользователь хочет фиксировать ситуации, когда:

* что-то приобретает;
* что-то делает;
* происходит какая-то операция;
* есть детали, которые полезно запомнить;
* нужна дата;
* потом нужно иметь возможность вернуться и вспомнить.

Примеры домена:

* быт;
* поездки;
* оформление документов;
* покупки;
* организационные действия;
* административные процессы.

Смысл:

```txt
событие произошло -> записать дату и детали -> потом можно найти и вспомнить
```

Это ближе к `Log`, `Record`, `Event`, `Memo`, `ActivityEntry`.

## 5. Сценарий 3 - Budget

пользователь хочет вести бюджет.

Функции:

* фиксировать поступление средств;
* фиксировать все запланированные расходы;
* не забывать обязательные траты;
* подписывать записи датами;
* добавлять теги;
* добавлять комментарии;
* поддерживать мультивалютное суммирование;
* повышать UX через автоматический пересчёт.

Смысл:

```txt
деньги пришли -> расходы запланированы -> система показывает картину -> ничего не забыто
```

Ключевые поля для бюджетных записей:

```txt
amount
currency
date
tags
comment
status
type
```

Возможные типы:

```txt
income
expense
planned_expense
```

Но это ещё не утверждённая модель.

## 6. Сценарий 4 - Reminder system

пользователь хочет reminder-систему

Главное требование:

> к напоминанию можно привязать любую сущность системы.

Примеры:

* budget entry;
* note;
* memo;
* памятка;
* запись;
* счётчик;
* checklist item;
* любая другая сущность.

То есть reminder должен быть не изолированной сущностью, а универсальным механизмом поверх системы.

Смысл:

```txt
любая сущность -> можно создать reminder -> система напоминает
```

Архитектурно это похоже на polymorphic relation:

```txt
Reminder.targetType
Reminder.targetId
```

Но техническое решение ещё не принято.

## 7. Сценарий 5 - Connectors / Integrations

пользователь хочет иметь возможность подключать:

* API соцсетей;
* боты;
* другие коннекторы;
* внешние каналы взаимодействия.

Пример:

```txt
Telegram bot
```

Цель:

```txt
упростить взаимодействие с системой
```

То есть пользователь не обязан всегда заходить в UI. Он может писать в Telegram-бот, а бот будет создавать заметки, напоминания, бюджетные записи и т.д.

Потенциальный смысл:

```txt
Input Channels
```

или:

```txt
ConnectorModule
```

## 9. Сценарий 7 - учёт расходуемых вещей

пользователь хочет вести подсчёт расхода исчерпываемых сущностей.

Пример: препараты, назначенные психотерапевтом.

Но домен шире: это не только лекарства, а любые расходуемые вещи.

Примерная сущность:

```txt
ConsumableItem
```

или:

```txt
ResourceCounter
```

Смысл:

```txt
есть ресурс -> он расходуется -> система считает остаток -> предупреждает, когда заканчивается
```

---

## 10. Пример с препаратами

Для каждого препарата могут быть параметры:

* дозировка;
* единица измерения;
* миллиграмы;
* общее количество элементов в упаковке;
* дозировка одного элемента;
* дозировка в момент приёма;
* остаток в миллиграммах;
* остаток в штуках;
* alert threshold.

Пример:

```txt
Миртазапин
alert = 5 таблеток
```

Когда остаётся 5 таблеток, система должна уведомить:

```txt
сущность исчерпывается
```

---

## 11. Расчёт расходуемого ресурса

Для препарата нужно считать:

```txt
остаток после приёма
```

В двух измерениях:

```txt
1. сколько мг осталось
2. сколько элементов упаковки осталось
```

Пример логики:

```txt
totalPackageItems = 30 tablets
dosagePerItem = 15mg
intakeDose = 15mg

after intake:
remainingItems -= 1
remainingMg -= 15
```

Но если дозировка приёма может быть меньше таблетки, например половина таблетки, тогда нужна дробная логика:

```txt
intakeDose = 7.5mg
dosagePerItem = 15mg

consumedItems = 0.5
remainingItems -= 0.5
remainingMg -= 7.5
```

## 12. Связь счётчиков с reminders/checklists

пользователь хочет, чтобы счётчики можно было привязывать к реальным сущностям.

Например, есть ежедневное напоминание со списком:

```txt
Миртазапин 15мг
Ламотриджин 50мг
Пароксетин 10мг
Кветиапин 25мг
```

Для каждой строки checklist привязан свой counter.

Когда пользователь зачеркивает пункт, например:

```txt
Миртазапин 15мг
```

система должна:

```txt
1. отметить пункт выполненным
2. найти связанный счётчик
3. списать нужное количество
4. пересчитать остаток
5. проверить alert threshold
6. если остаток <= threshold, создать alert/notification
```

Это важная связка:

```txt
ReminderChecklistItem -> ConsumableCounter -> DecrementOperation -> Alert
```

## 15. Core идея системы

Главная идея:

```txt
зафиксировать -> связать -> напомнить -> найти -> не забыть
```

Система должна быть личной внешней памятью.

Она должна работать с разными типами сущностей:

* заметки;
* события;
* бюджетные записи;
* напоминания;
* дневниковые записи;
* счётчики ресурсов;
* checklist items.

---

## 16. Важная архитектурная ось

Ключевая идея из сырых мыслей:

> Reminder должен уметь ссылаться на любую сущность.

И похожая идея:

> Consumable counter должен уметь связываться с checklist item / reminder item.

То есть в проекте явно появляется модель связанных сущностей.

Возможная доменная абстракция:

```txt
Attachable Entity
```

или технически:

```txt
entityType + entityId
```

Но пока это не решение, а выявленный паттерн.
